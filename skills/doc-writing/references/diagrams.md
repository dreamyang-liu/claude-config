# Diagrams

When a document explains architecture or a graph relationship, draw an SVG figure. Text alone
makes the reader build the graph in their head. A figure shows the graph at once.

## When to draw

Draw an SVG figure when the text explains a structure of nodes and connections, for example:

- architecture: components, their boundaries and the connections between them
- data flow or control flow between components
- dependencies between modules or services
- trees, such as the fork tree of a rollout and its branches
- state graphs, such as job states and their transitions

Draw the figure as SVG. Do not use ASCII art or Mermaid instead.

A linear sequence of steps is not a graph. Write it as a numbered list.

## Figure and text together

The figure shows the structure. The text still carries the point and the exact behavior:

1. Before the figure, write the point in NASA style. Refer to the figure in that paragraph.
2. Under the figure, write a caption of one sentence. The caption states what the figure shows.
3. After the figure, write the exact behavior in STE, or in a table. A reader can read an arrow
   in more than one way, so the conditions and the order must also be in the text.

The figure and the text must agree. Each node and each edge in the figure must appear in the
text, with the same name.

## Content rules

1. **One figure, one message.** If a figure needs more than about 12 nodes, split it. Draw one
   overview figure and one detail figure for each part.
2. **Use the names from the text.** Each node uses the same term as the text. Write names from
   the code in monospace, spelled as the code spells them.
3. **Give each relation type one line style.** If a figure has two relation types, add a legend.
4. **Label each arrow.** Write the function or verb first, then the condition. If one lead line
   in the figure gives the meaning of all arrows, short labels are enough.
5. **Keep one main direction.** The main flow goes left to right or top to bottom. Back edges,
   such as a retry or feedback, go the other way.
6. **Draw boundaries.** Draw each boundary, such as a host or a sandbox, as a labeled rectangle
   around its nodes.
7. **Avoid crossing lines.** Use orthogonal connectors with right-angle bends.
8. **Give each color a meaning.** Do not use color as the only signal. Also write the meaning as
   text, for example "terminal" in a state box.
9. **Name the source.** Write the code path that the figure was drawn from in a small line at
   the bottom.

## SVG rules

### Files

- Put a figure that a document uses in `docs/figures/<name>.svg`. Use a kebab-case name.
- Write a small figure by hand. Write a generator script when the layout needs computation, or
  when the figure will be regenerated. Put the script in `ops/figures/`. Make this comment the
  first child of `<svg>`:
  `<!-- generated by ops/figures/<script>.py; edit that, not this -->`
- Put drafts, preview PNGs and throwaway scripts in `scratch/`.

### Root element

The `<svg>` element has these attributes:

- `xmlns="http://www.w3.org/2000/svg"`
- `width` and `height`, and a `viewBox` that matches them
- `role="img"` and `aria-labelledby="title desc"`

Its first children are `<title id="title">` and `<desc id="desc">`. The `<desc>` describes each
node and each edge in prose. The `alt` text in the Markdown repeats it.

### Background

Draw an opaque background rectangle with rounded corners. On a dark GitHub theme, a transparent
SVG shows on a dark page, and the dark text disappears.

### Text

- Use `<text>` elements, so that the text stays searchable and diffable. Only brand figures,
  such as the logo, use glyph outlines from `ops/figures/typeset.py`.
- Use these font stacks:
  - sans: `-apple-system, 'Segoe UI', 'Noto Sans', Helvetica, Arial, sans-serif`
  - monospace: `ui-monospace, SFMono-Regular, Menlo, Consolas, 'DejaVu Sans Mono', monospace`
  - Chinese labels: put `'PingFang SC', 'Noto Sans CJK SC', 'Microsoft YaHei'` before the
    sans stack
- Make text at least 12 px at the displayed width. If the document shows the figure narrower
  than its `viewBox`, scale the minimum up. For example, a 1800-wide figure shown at 1000 px
  needs text of at least 22 units.
- Leave at least 20% spare width around each label. The reader's fonts are not your fonts.
- Define the styles once, as classes in a `<style>` inside `<defs>`. Define one arrowhead
  `<marker>`.

### Embedding

In `docs/*.md`, the path is `figures/<name>.svg`. In `README.md`, it is
`docs/figures/<name>.svg`.

```html
<p align="center">
  <img src="figures/<name>.svg" width="900" alt="<the same description as the SVG desc>"/>
</p>
<p align="center"><sub><one-sentence caption that states what the figure shows></sub></p>
```

## Check the figure

Do these steps before you finish:

1. Parse the file:
   `python3 -I -c "import sys, xml.etree.ElementTree as E; E.parse(sys.argv[1])" <file>.svg`
2. Render it at the displayed width:
   `rsvg-convert -w <width> <file>.svg -o scratch/<name>.png`
3. Look at the PNG with the Read tool. Check each of these:
   - No text overlaps a line or other text.
   - No text is clipped at an edge.
   - Each arrow ends at a box edge and points the correct way.
   - Each node and each edge from the text is in the figure.
4. Check each node and each edge against the code, as for an STE statement.

## Example

`run-store-states.svg` is the state graph for example 4 in `examples.md`. It shows these rules:

- a lead line that tells the reader how to read the arrows
- one line style, because all edges are transitions
- labels with the function first and the condition second
- colors with a text meaning, such as "terminal"
- a source line and a full `<desc>`
